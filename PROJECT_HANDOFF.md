The intended result is one local browser interface for operation and configuration, with management separate from Activity. This supersedes launcher-based management. The user selected sidebar navigation and dark mode, but dislikes the current theme/UI; detailed visual design will be handled separately later. Selection of the layout does not approve its current palette, detailed controls, or every section's contents.

### User-confirmed workflows

- Standing direction: use established concepts, patterns, and workflows, taking inspiration from similar apps rather than reinventing familiar solutions. Existing software/libraries are acceptable where useful, not a preferred approach in themselves. This principle does not settle individual workflow choices. Rework or starting over remains open for discussion when justified; no rewrite or framework change is automatically authorized.
- A desktop shortcut quietly starts/reuses the local server and opens the browser: setup on first use, Activity on later launches. Guided setup reuses Settings/Connections controls and remains reopenable from Settings.
- Setup uses a reopenable checklist linking to the existing Settings/Connections controls instead of fixed sequential steps. The user delegated checklist versus wizard selection; local configuration readiness is implemented; connected access remains an explicit separate check.
- Setup uses open access with gated operation: users may leave incomplete setup and open Activity; real viewer processing remains disabled until its prerequisites are met, with an explanation of what is missing. Local demo/testing remains a separate explicit action outside Activity. Per-operation local readiness is implemented; Twitch readiness belongs to the later phase.
- Navigation uses Activity, Connections, and Settings. Activity is for briefly checking current/waiting work and playback intervention in a mostly unattended stream utility. Every visible element needs a purpose.
- Closing the audio-owner tab cancels active work and pauses the queue; the server stays running. Reopening requires Resume. Explicit shutdown belongs in Settings → Application.
- Local browser Settings may accept API keys for private backend storage. Never return saved keys to the page; show configured/not-configured metadata afterward. AGENTS.md reflects this approved entry flow.
- Settings changes let the current request finish with its original settings, then apply before the next request starts. Waiting work stays queued; preserve character selection, cancellation, bounded queues, and late-result rejection.
- Save validates and stores settings locally. Connection checks and response/voice tests are separate explicit actions. Saving never invokes providers or creates Twitch rewards. The existence of these controls does not authorize live trials or account actions.
- Settings use Save per section, rather than one Save all. Unsaved edits survive navigation within the open tab and apply only on Save; Discard changes restores saved values. Warn on closing/refreshing with unsaved edits where supported. Unsaved API keys stay only in page memory. Show Unsaved changes while editing, Saved—applies after the current request while work is active, and Saved and active once applied. Validation failures explain the field error and preserve previous working settings.
- Changes that require a server restart are saved with explicit Restart required feedback; saving never restarts automatically. Restart app is an explicit action. If active/waiting work exists, explain that restart cancels it and clears the queue before proceeding. After restart, processing requires explicit Resume. Provider/model/voice changes still follow the agreed next-request application behavior; the server port is a developer environment setting outside browser Settings; saved default volume applies on next launch.
- Guided setup, general diagnostics (useful status and redacted errors), and explicit shutdown belong in Settings → Application. Provider and Twitch check results appear beside their respective controls. The user delegated this placement choice; local integration is implemented.
- Twitch connection remembers the user's explicit choice: reconnect on later launches after connecting; an explicit Disconnect keeps it disconnected. Reconnection never creates a reward or resumes a paused queue. Live authorization/setup remains deferred.
- Prerequisite handling should detect missing/incompatible dependencies and offer explicit install/repair/update actions, carrying forward assisted setup rather than only directing users to fix things manually. Explain material tradeoffs before excluding an assisted action. A small launcher setup prompt handles prerequisites that prevent the local server/browser interface from starting (such as missing Node or essential app dependencies); remaining assisted setup belongs in the browser. This approves the workflow, not installations or updates during this discussion. Node/dependency bootstrap is implemented. The user subsequently separated Codex installation/sign-in from app setup; Codex is prepared externally and only its local prerequisites are checked in the app; newer Codex versions still require the dialogue-only boundary check before use.
- Compact rows show each question once; expansion reveals only its response. Waiting entries without a response need no dropdown. Past entries are read-only, with no replay or dedicated review workflow. Development controls, testing, and Quit do not belong on Activity.
- Viewers choose a personality through one shared Channel Points reward using `Name: question`. Each personality has an assigned voice. Missing/unknown names are rejected and refunded after Twitch confirms; no default character. Tyrone is the first example; adding profiles is supported.
- Initial characters are a prompt plus assigned voice, with minimal name/identifier metadata for selection. File-based profiles are sufficient; no browser Add/Edit character interface is required initially. Exact file layout is not mandated. Final prompt/persona and voice evaluation remain deferred.
- Viewer questions are for live streams only: do not accept offline submissions for a later-stream backlog. Local testing remains available independently. This does not settle what a short playback pause during a live stream does to new submissions, or the exact stream-end handling of active/waiting work.
- TTS donation/subscription-alert workflows are the main reference for routine operational patterns. Use their established concepts to inform recommendations; do not assume one universal offline/queue policy or add donation/subscription features to scope.
- Implementation sequence is local-first: finish browser configuration, local testing, queue, and playback independently of Twitch configuration; retain existing modular Twitch code for later integration rather than remove/rebuild it. Twitch authorization, reward setup, and live/offline intake integration follow afterward. The user subsequently authorized the proposed local integration plan. Live provider/OBS work remains unauthorized.
- Functional pieces precede final model selection, quality evaluation, persona/prompt editing, voice selection, and fine-tuning. Easy model switching matters; generation and hosted speech remain independently replaceable.
- The initial connected functional trial uses a free OpenRouter model after discussing and verifying free access. No final model, paid account, funded balance, budget, spending, or paid fallback is authorized.

## Current implementation

The user approved the concrete local browser-management plan after discussion. That local milestone is implemented using the existing Node/TypeScript server, queue, provider adapters and file catalog; no framework/dependencies were added.

- Production browser uses the selected dark sidebar: Activity, Connections, Settings and reopenable checklist. Persistent navigation preserves audio ownership and in-memory drafts. Activity has compact question rows, response-only expansion, intervention controls and read-only history. Testing/shutdown are in Application.
- Backend-owned SettingsStore validates fixed section schemas and atomically writes existing private generation/speech files plus app.json for setup progress and launch-volume default. Server port is configured through TYRONE_PLAYBACK_PORT before launch; legacy app.json port entries are ignored. Unrelated env values and inherited override precedence are preserved. Saved keys/voice IDs never return to the page; blank replacements retain them. Save makes no connected calls.
- Missing provider settings no longer block management startup. No implicit provider/model selection is made for new management. Full requests and independent tests have per-operation local configuration gates. Managed startup is paused. Demo is synthetic; normal/demo entrypoints do not load/connect Twitch.
- Active requests pin their pipeline for generation and speech. Saved provider/model/voice changes apply before the next request starts, preserving queued character identity. Invalid saves retain previous settings. Restart is explicit and bounded, cancels/clears work with confirmation when needed, and requires Resume afterward. Playback defaults apply on launch. The port form, public port/restart-required metadata and browser port-save handling were removed.
- Separate controls implement read-only API-key checks, generation-only response tests and fixed-phrase voice playback tests. These normal-mode actions contact/use providers only when explicitly invoked. Codex has a single prerequisite check verifying executable/version only, not sign-in or allowance. Actual installations/sign-ins and connected checks/tests were not run in this milestone.
- Launcher bootstrap offers explicit Node/dependency installation when startup is blocked. Codex preparation is external; the browser only checks its local prerequisite version. Installer controls, endpoint, PowerShell Codex actions and background setup state were removed. CLI remains exactly 0.162.0; other versions require offline boundary verification first. Private CLI path overrides remain supported.
- Superseded mockup files, preview command, old management wizard and unused styles were removed. Node/dependency bootstrap, later-stage CLI audition/export scripts and modular Twitch tooling remain for their current/later purposes. Build/package inputs include the production interface; private/recovery state remains excluded.
- Build, all twelve test files including guarded installed CLI boundary, formatting and PowerShell syntax passed. Isolated browser checks verified drafts, secret-field clearing, durable saves, error-feedback retention, synthetic completion and secondary-tab silence at 1280px. Small-screen resize and screenshot capture failed; final visual/small-screen review is unverified. See verification for evidence.

Repository remains private Joseph2xy/placeholder, branch master; naming remains temporary. No live provider trial, installation/sign-in, Twitch account action, spending or OBS setup occurred during integration.
